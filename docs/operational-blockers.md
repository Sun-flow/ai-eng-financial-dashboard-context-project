# Operational Blockers — Issues Preventing Proper Operation

> Identified: September 23, 2026
> Priority: Critical (prevents or disrupts running the project)

---

## 🔴 Critical — Definitely Preventing Proper Operation

### 1. Backend `--reload` Flag Causes Restart Loop (Docker)

**File:** `backend/Dockerfile`
```dockerfile
CMD ["python", "-m", "debugpy", "--listen", "0.0.0.0:5678", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--reload"]
```

**Problem:** The `--reload` flag makes uvicorn watch the `/app` directory for file changes. When combined with the bind mount volume in `docker-compose.yml`:

```yaml
volumes:
  - ./backend:/app
```

The reloader detects file writes generated by Python itself (`.pyc` bytecode caches, `__pycache__` directories, temp files) and triggers a restart. Each restart writes more cache files, triggering another restart — an **infinite restart loop**.

**Severity:** 🔴 **Critical** — Container never stabilizes.

**Fix:** Remove `--reload` from the Docker CMD (it's only needed for local development without Docker).

### 2. Vite Proxy `backend:8000` Won't Resolve Outside Docker

**File:** `frontend/vite.config.ts`
```ts
proxy: {
  "/api": {
    target: "http://backend:8000",  // Docker service name
    changeOrigin: true,
  },
},
```

**Problem:** The Vite proxy target is hardcoded to `http://backend:8000`. The hostname `backend` only resolves inside Docker Compose's internal network. When running the frontend locally (without Docker), `backend` does not resolve and the proxy fails — all API calls return 502 errors.

**Severity:** 🔴 **Critical** — Frontend works in Docker but is completely broken when running locally.

**Fix:** Use an environment variable for the proxy target, or default to `http://localhost:8000` for local development.

### 3. Mock Data Year Mismatch (Today's Date vs. UI Label)

**File:** `backend/app/routes.py` (line: `_year_for_month`)
```python
def _year_for_month(month: int, today: date) -> int:
    if month < today.month:
        return today.year
    return today.year - 1
```

**Problem:** `generate_mock_movements(seed=42)` calls `date.today()` (September 23, 2026). Due to the `_year_for_month` logic:
- **Jan–Aug:** Uses year **2026** (month < 9)
- **Sep–Dec:** Uses year **2025** (month >= 9)

So generated data spans **Sep 2025 → Aug 2026**. But the dashboard header says:

```tsx
<DashboardHeader period="2024 - Full Year" />
```

**Severity:** 🟠 **High** — The app runs, but shows incorrect year labels to users.

**Fix:** Either hardcode a specific year in the mock data generator, or make the header dynamic based on actual data.

### 4. `depends_on` Without Health Check — Race Condition on Startup

**File:** `docker-compose.yml`
```yaml
depends_on:
  - backend
```

**Problem:** Docker Compose `depends_on` only waits for the container to *start*, not for it to be *ready to accept connections*. The frontend container may start and send API requests before the backend's uvicorn server is listening on port 8000. The frontend's error state handles this gracefully, but it creates a poor first-run experience (flashing error state or loading skeletons that never resolve).

**Severity:** 🟡 **Medium** — Causes transient errors on first startup.

**Fix:** Add a healthcheck to the backend service and use `depends_on: backend: condition: service_healthy`.

## 🟡 Medium Severity

### 5. `debugpy` + Python 3.13 Compatibility Unknown

**File:** `backend/Dockerfile`
```dockerfile
FROM python:3.13-slim
```

**Problem:** Python 3.13 introduced significant CPython internals changes (PEP 703 free-threaded mode groundwork, JIT compiler work). `debugpy` is a debugger that hooks deep into CPython. If the installed `debugpy==1.8.22` doesn't fully support Python 3.13, it could crash on import or fail to attach, taking down the container.

**Severity:** 🟡 **Medium** — May or may not be an issue depending on debugpy's 3.13 support status.

**Fix:** Pin to `python:3.12-slim` if debugpy fails, or test with 3.13 first.

## 🔶 Deferred / Paused — Inter-Container Networking Broken (10)

> **Status as of 2026-09-23: PAUSED.** The build/restart-loop issues (#1, #4) are FIXED (see notes below), but a separate, unresolved blocker prevents the Docker stack from serving data.

**Symptom:** `docker compose up` starts both containers and the backend reports `Healthy`, but the **frontend UI loads forever** (never receives `/api/metrics` data).

**Root cause (diagnosed):** Frontend ↔ backend containers **cannot route to each other** over the compose bridge network, verified in both directions:
- Frontend container → `backend:8000` and backend IP `172.18.0.2:8000` → **time out**
- Backend container → frontend IP `172.18.0.3:5173` → **time out**
- Each container reaches its own loopback and own IP fine; all services healthy individually → the break is purely inter-container routing.
- `ip_forward=1`; network has no special options (`internal=false`); ICC not disabled; yet traffic is blocked. Suspected host/DinD-level firewall (`iptables` not inspectable without root) or nested-Docker bridge breakage.

**Tried without success:** `docker compose down` → `docker network prune -f` → `docker compose up -d` (fresh network + containers). Cross-container timeouts persisted.

**Recommended future path (deferred):** Fix host bridge/iptables state, or run frontend outside Docker pointed at `localhost:8000` via `VITE_API_PROXY_TARGET`.

## Notes — Recently Confirmed Fixes

- **#1 (`--reload` restart loop)**: `--reload` removed from the **development** target CMD in `backend/Dockerfile` (previously it was only removed from production; the dev target — used by `docker compose up` — still looped).
- **#4 (healthcheck)**: `python:3.13-slim` has **no `curl`**, so the compose healthcheck always failed. Added `apt-get install curl` to the `base` stage. Backend now reports `Healthy`.
